# Local operations and proposed private deployment gate

Nothing in this runbook authorizes external setup, deployment, payment or release.
Use [local setup](../pilot/README.md) and [architecture](./V0.1_ARCHITECTURE.md).

## Private data and local recovery

Default `.local/` is gitignored. Owner password verifier, profiles, session state,
cache, SQLite sidecars and backups stay there. Directory creation requests mode
0700 and DB mode 0600; existing parent-directory permissions remain the operator's
responsibility. Never publish that directory, actual preview URLs or credentials.
No encryption-at-rest service is configured by this implementation.

Schema v1 initialization is additive only for a new pilot database. Compatibility
files/caches are not migrated or deleted. Unsupported versions or corrupt stores
fail closed; no silent reset. Always back up before a future migration. A future
schema change needs an explicit migration + backward/rollback test; no such
version upgrade is implemented or claimed here.

Manual backup (choose a destination that does not exist):

```sh
python3 -m pilot.maintenance backup --source .local/pilot.sqlite3 --destination .local/review-backup.sqlite3
```

Uses SQLite's backup API and integrity_check, with exclusive destination creation,
and never overwrites source/owner files. Backups contain private owner data and
verifiers, not just articles. Store privately; retention for backup media is not
implemented as an unattended service. A failed copy can leave a reserved destination;
inspect it rather than silently overwriting/deleting owner files.

Restore to a **new** private path, after stopping the old serving process:

```sh
python3 -m pilot.maintenance restore --source .local/review-backup.sqlite3 --destination .local/restored.sqlite3
python3 -m pilot.app serve --data .local/restored.sqlite3 --port 8766
```

Restore verifies schema/integrity, performs startup expiry recovery, invalidates
all copied sessions, fails copied in-flight runs and imposes a conservative refresh
delay. Sign in again with the existing local password. It does not overwrite the
original DB or resurrect its cookie sessions. Use the Private HTTPS origin option
when testing through Codespaces. Tests exercise copy/restore with synthetic data;
no actual owner database/backup was created for the test report.

Local rollback: stop the new process and select the preserved earlier code/data
snapshot in a separate directory or approved branch operation. Keep the current
uncommitted implementation until reviewed; no reset/clean, owner-data deletion,
old-schema startup or branch destruction is required. This task performed no
destructive rollback or deployment.

## Proposed deployment runbook — not executed

1. Review the exact local implementation and actual browser results. Publication
   would need separate authorization and explicit staged-file leakage review.
2. Establish provider rights for the exact minimal fields, recurring requests,
   hard rolling retention, backup policy and private attribution. Keep live mode
   blocked until that evidence and a bounded request budget are approved. Verify
   both CA/US once and once again at an appropriate permitted interval; test the
   real-card browser view without treating fixtures as live compatibility.
3. Select one supported private host/backend/database after verifying current
   free-tier eligibility, billing/cost controls, persistence, transaction/lease
   semantics, DNS/deadline protections and recovery limits. No such account,
   free-tier entitlement, production cost or infrastructure is verified here.
4. Obtain explicit approval for the selected infrastructure, required account/
   external writes, credential setup and deployment. Do not treat the current
   local Python HTTP server as an internet production deployment entry point.
5. Provide reviewed production HTTPS termination, owner-only authentication and
   authorization, secret storage, actual Secure/session/CSRF behavior and private
   API cache policy. Either harden/test the chosen owner auth integration or
   establish a separately approved provider integration; never replace it with
   a mock, public preview or JS token. Validate denied anonymous reads/writes.
6. Deploy only the authorized reviewed revision to private access. Verify actual
   environment/commit/HTTPS origin, logout/device data handling, bounded real
   refresh/retention, failed/empty states, actual Chromebook and Android checks,
   and no sensitive logs/screenshots/public cache. Keep all actual URLs and secrets
   out of public evidence. Record sanitized findings and failures separately.
7. Before rollout, prove backup/restore and rollback against the selected DB/runtime.
   Keep an approved previous revision and compatible private backup; reject
   unsupported schema downgrades. Verify restored-session invalidation. Record
   owner release approval explicitly. No automatic progression to V0.2.

Until those release gates pass, the result is a local synthetic-data development
slice with real local authentication, not a production service or approved daily
live reader.

## V0.1.1 operational-readiness amendment

The preceding V0.1 runbook is historical planning. The
[current bounded RSS policy](./V0.1.1_SOURCE_POLICY.md) now permits the narrow
single-owner temporary reader interpretation; this does not authorize deployment
or broad reuse. Live-store backup/restore is refused before a destination is
created. Keep the above backup procedure for synthetic stores only.

Schema version remains 1, with an additive `request_attempts(source_id, started)`
ledger and policy config revision 2. It retains attempt timestamps for a rolling
24h, separately from the bounded run display. Startup fences old workers and
removes old validators on config revision change. It does not change an existing
store's mode, clear its rate-limit ledger or discard unrelated/owner data. Do not
roll live stores back to V0.1 code: it lacks the new policy and budget enforcement.
No downgrade, destructive migration or deployment was performed.

Current hosting assessment and the single consolidated owner session are in
[operational readiness](./V0.1.1_OPERATIONS.md). Historical acceptance grades in
[V0.1 evidence](./V0.1_EVIDENCE.md) remain unchanged; current observations belong
in [V0.1.1 evidence](./V0.1.1_EVIDENCE.md).
