## 4. V0.1 product slice (only after Gate A and development approval)

Objective: a private personal enhanced RSS reader that shows cached Brickset articles immediately, then performs an eligible refresh on opening/foreground/manual request. Both CA/US feeds, one simple editable persisted profile (name, enabled markets/sources, include/exclude keywords, lookback, refresh preference), compact Deals and Manage/Settings surface. No full profile lifecycle yet; V0.2 retains create/edit/duplicate/pause/resume/archive/restore/delete, tags, wishlist, thresholds, source settings, save/dismiss and offline view. Avoid dead future controls. Article cards are clearly labeled aggregate articles; link out to original article, preserve affiliate parameters; no current price, stock, seller, expiry, historical low or discount qualification invented. Numeric rules and reliable product/set matching belong to V0.1.1 before V0.2 if supported. Source timestamps, native market and last-success/attempt labels are visible. A failed check is not an empty feed and absent items do not prove expiry. Make the layout usable on Chromebook and Android.

### Architecture and stack decision

Use one backend and one persistent store; retain narrow modules for fetch, normalize, store, refresh coordination, matching and presentation. Preserve existing compatibility directory as an executable reference; do not promote prototype HTTP server or permission override unchanged. Choose the smallest defensible runtime after inspecting actual environment, dependencies and candidate private hosting/DB constraints; GitHub + Cloudflare Workers/Static Assets/D1 remains an R2 candidate, not a selected or provisioned stack. Python prototype does not require a Python production stack. Compare existing-runtime portability, managed storage, authentication, free-tier cost, server-side safe retrieval, transaction semantics and Chromebook setup. Document decision and reject unnecessary services; if choosing a host would require account creation, charges or external configuration, defer those actions and deliver local implementation plus reproducible plan. No new services or paid fallback. Do not introduce queue/scheduler/AI service.

### Minimal logical contracts

- Source: fixed ID, market, allowlisted exact endpoint, enabled/permission scope, retention policy, effective TTL, lastAttemptAt, lastSuccessAt, outcome, nextEligibleAt, validators if present. Two Brickset configurations. Slickdeals disabled and excluded from fetch paths. No arbitrary user URL input.
- Article: stable source-scoped ID derived from native ID or canonical article URL, title, market, publishedAt nullable, observedAt, firstSeenAt/lastSeenAt if retained, original evidence link, bounded permitted metadata, content revision/hash, explicit `recordKind` article, verification reported/unverified and availability unknown. Preserve source evidence separately from interpretation. R2 optional money/price/reference basis/discount/expiry/merchant/product fields stay null absent evidence; no floating-point money. Do not normalize one article to one deal/price. Preserve source/affiliate link; no raw article archive by default. Future offer mapping uses distinct stable market/product/offer identity and provenance; no new offer extraction scope now.
- Profile: one editable persisted record with revision, explicit market/source applicability, simple literal case-insensitive matching, exclusions, lookback, refresh preference. Editing filters rematches cache without unnecessary network calls. Do not store owner profile in public Git.
- Run: ID, trigger, scope, lease/idempotency, source configuration revision, start/end, result, safe error category, counts. One fetch per eligible source, not per profile. Success-empty, unchanged, changed, skipped, failed and partial distinguishable. Shared state is authoritative server-side; private API responses are not public cacheable. Logical APIs may be GET /deals, GET/PATCH /profile, GET /sources and POST /refresh; use minimal actual surface, version schema and owner-scope all reads/writes.

### Refresh, retention and permissions (release-critical)

Use a provisional 30-minute minimum freshness interval only if permitted; it is not a retention license or a guaranteed provider limit. No unattended polling, no auto-fetch on every view when fresh, no model calls. Render cache then check eligibility; enforce server-side freshness, in-flight lease, bounded retries/backoff and Retry-After, safe error handling and atomic updates. Concurrent opens must not duplicate work. Conditional headers only when supplied; both live endpoints previously lacked validators. Repeat real retrieval once at an appropriate permitted interval during authorized validation; if not possible, report unverified. No absence/availability inference from HTTP failure or rolling feed windows.

Before storing real data beyond an ordinary temporary reader session, document a defensible permitted purpose, specific bounded fields, retention duration, expiry/eviction behavior, attribution and access restrictions. Do not turn prior 180-second validation session or proposed 30-minute TTL into permission for long-term storage. Prefer a small rolling snapshot of latest permitted metadata with hard age/count limits; preserve last-good within retention, not forever. Store only minimum required links (avoid unnecessary embedded per-offer URLs), never raw feed bodies, images or full descriptions without established rights. Source failures must not extend content retention indefinitely. Expire records independently of source freshness; show stale/unknown/expired distinctly. Do not delete unrelated caches or owner data. If ordinary private reader persistence remains ambiguous, disable persistent live mode, use temporary/in-memory session plus synthetic durable cache for development, mark production persistent-cache gate HOLD and propose narrow owner-approved clarification. Saved owner references/configuration in V0.2 must respect source terms; no auto purge of owner-created content without policy. Historical pricing and long-term deal archive deferred.

## 5. Specific remediation from reviewed code

Implement only changes required by the V0.1 slice, not a wholesale compatibility rewrite. Validate behavior with regression tests.

| Finding in pinned prototype | Required disposition |
|---|---|
| `brickset_reader.py::fetch_once` ledger permanently reserves one initial GET per market for handoff | Keep compatibility ledger intact. Production uses separate permission-bounded coordinator with transaction/lease, TTL and explicit budget. Never bypass original guard. |
| `feedcompat.py::Cache.refresh` merges old/incoming records without eviction; reader cap is ten | Rolling bounded snapshot / age and count policy; test changed feed, failure within retention, expiry and repeated refresh. Separate user state from cached source metadata. |
| `retrieve` checks monotonic deadline around blocking operations; DNS and socket phases may exceed intended total | Enforce platform-appropriate hard overall deadline or explicitly documented bounded phase limits and cancellation, DNS/redirect safety, bytes/count bounds, no unapproved redirect or private/metadata destination. Test slow/bad transport. |
| `ReaderCache` expiry and TemporaryDirectory cleanup rely on process lifecycle; abrupt death may leave files | Enforce expiry on read and recovery of owned expired cache; do not delete unrelated files. Test restart/abandoned cache and atomic recovery. |
| `inspect_records` strips summary, retains provenance links and hashes only retained metadata | Minimize retained links and preserve attribution; version based on visible material article fields only; clearly state offer-content changes may be missed until permitted offer extraction. Do not promise product-level updates yet. |
| `HTTPServer` preview bound loopback, no app authentication; CSP/escaping present | Do not expose prototype server publicly. Production requires actual owner auth/authz, session and request security. Retain CSP, escaping, no executable feed markup. |
| `safe_link` rejects literal private IP and localhost but does not resolve arbitrary display URLs | Keep user-visible source links distinct from server fetch destinations; constrain actual clickable links to expected safe HTTPS source/merchant origins where appropriate, validate and escape. Never fetch links server-side to enrich articles. |
| Generic cache `lastSuccessAt` uses refresh start timestamp and global local file lock | Use clearly defined attempt/observed/completion semantics and suitable transactional source-scope lease; prevent stale completion overwriting newer state. |

Security tests: permission-denied before transport; fixed HTTPS endpoint allowlist, TLS hostname validation, safe redirects and DNS/private/link-local/metadata protection appropriate to runtime; bounded XML parser rejects DTD/entity and malformed/oversized/deep payloads; no unsanitized HTML; auth required for read/write and owner scope; CSRF where cookie-based; no tokens/keys in JS, repo, logs, screenshots or evidence. No credentials requested in chat. Private device cache policy, logout clearing where applicable. Verify unauthorized access fails; no fake auth accepted for release. Local-only mock auth is clearly labeled and never deployment-ready.
